Lesson 3: loops and goals - the agent that stops on purpose

Today your agent takes several steps in order, then stops for a reason you chose. Lesson 2's loop had one way out: the model stopped asking for tools. That exit belongs to the model, not to you. You'll add three of your own, a turn counter, a goal your code can check, and a timeout on every tool. You'll also add a report_status tool, so when the model thinks it's done it says so in an enum your code can test, not in a sentence you have to read. And you'll do the math on why the counter alone saves $2.18 per run. The loop is about forty lines in JavaScript and Python. The rest is tool schemas. Same API key you already have.

The one idea

One tool call is a transaction. A loop with an exit is an agent. Lesson 2 built the loop. This lesson is about the exit, because that's where agents go wrong in front of real users. An agent that can't tell it's finished runs up a bill. An agent that thinks it's finished three steps early says the job is done and leaves the file half written. Same bug, opposite directions.

There are four ways out of the loop, and only one of them belongs to the model:

  • The model says so. stop_reason comes back as end_turn. Better: it calls your report_status tool and says "complete" on purpose.
  • Your counter says so. Turn 12 of 12. You stop, and you log that you stopped at the limit rather than at an answer.
  • Your goal check says so. The model reported "complete", and your own four lines of code looked: the file exists and has three lines. Nothing left to do.
  • Something broke and you decided. A tool hung, a reply got cut off, a request was refused.

Lesson 2 only had the first one. This lesson adds the other three. To write them, you need to know every value stop_reason can hold.

stop_reason, and every value it can hold

Every reply carries one. if (stop_reason !== "tool_use") was fine for one lesson, but it lumps five different situations together as “the model answered.” Two of them aren't that at all.

ValueWhat happenedWhat you do
end_turn The model has nothing more to say Check your goal. If it's met, stop. If not, say what's missing and go round again
tool_use It wants one or more tools Run them, answer all of them in one message, go round
max_tokens The reply hit your max_tokens limit and got cut off mid-sentence Don't add it to messages the last block may be half a tool call. Raise max_tokens and send the same request again
stop_sequence It wrote a string you listed in stop_sequences Nothing, unless you set that parameter. If you did, this is your own exit and you already know what it means
pause_turn A long server-side tool (web search, web fetch, code execution) was paused part way through Send the conversation back unchanged and the server picks up where it left off. Don't add a “continue” message
refusal A safety classifier declined the request. It arrives as HTTP 200, not as an error Read stop_details.category, stop the loop, tell the user. Sending the same prompt again won't help

Two details worth learning now instead of at 1am. First, stop_details is filled in only when stop_reason is refusal. Every other time it is null, so check before you read it. Second, pause_turn is the one most people hit by accident: the SDK tool runners don't resume it for you, so a paused turn ends the run and comes back looking like the final answer. No error, just a reply that stops early.

Other providers spell it differently and mean the same three things. OpenAI-compatible servers: including Ollama and vLLM send finish_reason with the values stop, length and tool_calls. Gemini sends finishReason. We convert all of them into one stopReason in js/llm.js, using four adapters (Anthropic, Google, OpenAI-style chat, and WebLLM running in the tab), so the loop above them doesn't have to care. Whatever you use, find this field. It's the only part of the response that tells you what to do next.

The turn cap, and what it saves

while (true) is a bug on a timer. A model has no sense that it's going in circles. Give it a tool description it misreads and it will call that tool again, and again, each time for a reason that looks sensible to it. And every one of those turns re-sends the whole conversation.

Do the math, because the math is the argument. Each stuck turn adds a tool_use block and its tool_result, call that 600 tokens, and the first prompt is 300 tokens. So turn 1 sends 300 tokens. Turn n sends 300, plus 600 for every one of the n − 1 turns before it. You pay for the whole pile every turn, not just the newest turn.

Let it run to 40 turns and you've paid for 480,000 input tokens and gotten nothing. At Claude Opus 5's $5 per million, that's $2.40. Stop at 12 and the same runaway costs 43,200 tokens, or $0.22. Four lines of code saved $2.18 on one request. Now run that agent a thousand times a day with one broken tool description: uncapped, that's $2,400 a day spent on turns that were never going to finish.

Pick a number, break at it, and log that you did. A capped runaway is a bug report. An uncapped one is an invoice.

Which number? Count the steps the task really needs, then roughly double it. Read, edit, verify is three tool calls and four turns, so twelve is generous. The harness ships with max steps 40, because it has no idea what you're about to ask for. An agent built for one job does know, and should use a smaller number.

A goal your code can check

The exit everyone forgets is this one: the model stopping is not the job finishing. end_turn means “I have nothing more to say.” That's a fact about the model, not about your files. If you want to catch the difference, something has to go and look, and that something is four lines of your own code.

So the goal has to be checkable. Most goals people give an agent are a feeling instead:

Two rules make this work. First, write the goal in the prompt using the same words your check uses, so the model aims at the thing you measure: “three lines” in the prompt, length === 3 in the code. Second, when the check fails after the model says it's done, tell it what's missing in one sentence and let it keep going. Don't start a new conversation, it already has the whole messages array.

Make “done” a tool call, not a goodbye

Your side of the exit is settled. The model's side is still end_turn, the weakest signal in the API: it only means “I stopped talking.” A finished job, a wandered-off agent, and a model that ran out of things to say two lines early all look identical. So give the model a tool to say it with instead.

One more schema, next to read_file and write_file. It doesn't change anything in the world. It exists so the model's opinion arrives in a shape your code can test:

{
  name: "report_status",
  description:
    "Report where you are against the goal. Call this after every write. " +
    "Use \"complete\" only when notes/paris.md holds exactly three lines " +
    "and you have read them back and seen all three.",
  input_schema: {
    type: "object",
    properties: {
      status:   { type: "string", enum: ["complete", "incomplete"] },
      progress: { type: "integer", minimum: 0, maximum: 100 },
      note:     { type: "string", description: "one line: what is left to do" },
    },
    required: ["status", "progress"],
  },
}

Two fields, doing two different jobs. The enum is the one that changes your loop. It has two allowed values, so status === "complete" is a real test instead of you interpreting a sentence. A model that would have drifted off with end_turn now has to pick a word, and picking "incomplete" commits it to keep working. An enum is also the cheapest constraint you can put in a schema, because “one of these two strings” is easy for the model to obey.

The progress integer changes nothing about the exit and everything about your logs. It's the model's guess, not a measurement, so print it and never test it: don't stop at 100, don't gate anything on 80. Look at the code below, there is no if on progress anywhere, just one console.log. What it gives you is a run you can skim afterwards. Three turns in a row at 60 means a stuck agent, and you'll see it long before the turn cap fires. A run that climbs 20 → 90 and then reports "complete" at 90 is telling you your prompt and your check describe different jobs.

Keep the end_turn branch anyway. A model that stops talking without ever calling report_status is the clearest form of “it gave up,” and now you can write that in the log instead of guessing.

Nudge once. If the model says complete and your check fails twice, the model isn't the problem. Either your check is stricter than your prompt, or your tools can't do the job you asked for. Stop and re-read both.

tip: run the check before the first turn

Call your goal function once before the loop starts. If it returns true, the task was already done and you were about to pay a model to find that out. If it throws, you just found the bug in your check for free, instead of at turn 12, where it returns undefined and your agent never stops.

The code, JavaScript

Complete and runnable. npm i @anthropic-ai/sdk, set ANTHROPIC_API_KEY, then run it with Node. Same three parts as lesson 2, the tools, their descriptions, the loop, with a goal and a counter wrapped around them.

import Anthropic from "@anthropic-ai/sdk";
import { readFile, writeFile } from "node:fs/promises";

const client = new Anthropic();

const MAX_TURNS = 12;             // your exit, not the model's
const TOOL_TIMEOUT_MS = 10_000;   // no tool is allowed to hang the run

// 1. the tools. Two touch the disk, one only reports.
let claim = { status: "incomplete", progress: 0, note: "not started" };

const TOOLS = {
  write_file: async ({ path, text }) => {
    await writeFile(path, text);
    return `wrote ${text.split("\n").length} line(s) to ${path}`;
  },
  read_file: ({ path }) => readFile(path, "utf8"),
  // what the model thinks, in a shape the loop can test
  report_status: (input) => {
    claim = input;
    return `noted: ${input.status} at ${input.progress}%`;
  },
};

const toolSchemas = [
  {
    name: "write_file",
    description: "Write text to a path, replacing whatever was there.",
    input_schema: {
      type: "object",
      properties: { path: { type: "string" }, text: { type: "string" } },
      required: ["path", "text"],
    },
  },
  {
    name: "read_file",
    description: "Read a file back and return its contents verbatim.",
    input_schema: {
      type: "object",
      properties: { path: { type: "string" } },
      required: ["path"],
    },
  },
  {
    name: "report_status",
    description:
      "Report where you are against the goal. Call this after every write. " +
      "Use \"complete\" only when notes/paris.md holds exactly three lines " +
      "and you have read them back and seen all three.",
    input_schema: {
      type: "object",
      properties: {
        status: { type: "string", enum: ["complete", "incomplete"] },
        progress: { type: "integer", minimum: 0, maximum: 100 },
        note: { type: "string", description: "one line: what is left to do" },
      },
      required: ["status", "progress"],
    },
  },
];

// 2. the goal. Written twice on purpose: in words for the model, in code for
//    the loop. Both say the same thing.
const GOAL = "Write notes/paris.md with exactly three lines about the weather, " +
             "then read it back and confirm all three lines are there. " +
             "Call report_status after every write.";

async function goalMet() {
  try {
    const text = await readFile("notes/paris.md", "utf8");
    return text.trimEnd().split("\n").length === 3;
  } catch {
    return false;              // no file at all just means "not yet"
  }
}

// 3. the loop. Four exits, three of them yours.
const messages = [{ role: "user", content: GOAL }];
let turn = 0, nudges = 0, budget = 16000, done = false;

if (await goalMet()) throw new Error("already done, nothing to run");

while (turn < MAX_TURNS) {
  turn++;
  const reply = await client.messages.create({
    model: "claude-opus-5",
    max_tokens: budget,
    tools: toolSchemas,
    messages,
  });

  // EXIT 4a: the reply was cut off. The last block may be half a tool call, so
  // don't add it to messages, raise the limit and re-send the same request.
  if (reply.stop_reason === "max_tokens") {
    budget = Math.min(budget * 2, 64000);
    console.warn(`truncated, retrying with max_tokens ${budget}`);
    continue;
  }

  messages.push({ role: "assistant", content: reply.content });

  // not an exit: a server-side tool paused part way. Send it all back unchanged.
  if (reply.stop_reason === "pause_turn") continue;

  // round again: run every call, answer every call, in one message.
  if (reply.stop_reason === "tool_use") {
    const calls = reply.content.filter(b => b.type === "tool_use");
    const results = await Promise.all(calls.map(runOne));
    messages.push({ role: "user", content: results });   // always answer every call

    // the meter is a log line, never a test. Print it and watch it move.
    console.log(`turn ${turn}: ${meter(claim.progress)} ${claim.note ?? ""}`);

    // EXIT 3: it said complete. Check the disk before believing it.
    if (claim.status === "complete") {
      if (await goalMet()) { done = true; break; }
      results.push(nudge());   // `results` IS that message, so the nudge goes with it
    }
    continue;
  }

  // EXIT 4b: refusal, stop_sequence, or some value added after this was written.
  // Crash loudly instead of treating it as an answer.
  if (reply.stop_reason !== "end_turn") {
    throw new Error(`unhandled stop_reason: ${reply.stop_reason} ` +
                    `${JSON.stringify(reply.stop_details ?? null)}`);
  }

  // EXIT 1: it stopped talking. If it never said complete, that's the "gave up"
  // case, and now it has a name in your log.
  if (claim.status !== "complete") console.warn(`end_turn at ${claim.progress}%`);
  if (await goalMet()) { done = true; break; }
  messages.push({ role: "user", content: [nudge()] });
}

// EXIT 2: the counter. Always say which exit you took.
console.log(done
  ? `goal met in ${turn} turn(s)`
  : `stopped at the ${MAX_TURNS}-turn cap, last claim ${claim.status} ` +
    `at ${claim.progress}%, ${claim.note ?? "no note"}`);

// one sentence saying what's missing, and the only place nudges are counted.
function nudge() {
  if (++nudges > 1) {
    throw new Error("said done twice, the goal, the check or the tools disagree");
  }
  const text = `notes/paris.md does not have three lines yet, you last ` +
               `reported ${claim.status} at ${claim.progress}%. Finish the job.`;
  claim = { ...claim, status: "incomplete" };   // used up: make it report again
  return { type: "text", text };
}

// the meter, for humans reading the log. Twenty cells, so each cell is 5%.
function meter(p) {
  return `[${"▓".repeat(Math.round(p / 5)).padEnd(20, "·")}] ${String(p).padStart(3)}%`;
}

// one tool call: give it a deadline, and send failures back as information
async function runOne(block) {
  const base = { type: "tool_result", tool_use_id: block.id };
  try {
    const out = await withTimeout(TOOLS[block.name](block.input), TOOL_TIMEOUT_MS);
    return { ...base, content: String(out) };
  } catch (err) {
    return { ...base, is_error: true, content: String(err.message) };
  }
}

function withTimeout(work, ms) {
  return Promise.race([
    Promise.resolve(work),
    new Promise((_, reject) =>
      setTimeout(() => reject(new Error(`timed out after ${ms} ms`)), ms)),
  ]);
}

If you read only one thing in that code, read the continue and break points. Each one is labelled with the exit it belongs to, and the last line of the run prints which exit you left by, along with the model's last status. That's the difference between an agent you can debug and an agent you can only watch.

The code, Python

The same program. pip install anthropic.

import anthropic
from pathlib import Path
from concurrent.futures import ThreadPoolExecutor, TimeoutError as Timeout

client = anthropic.Anthropic()

MAX_TURNS = 12
TOOL_TIMEOUT_S = 10
NOTES = Path("notes/paris.md")

# 1. the tools
def write_file(path, text):
    Path(path).write_text(text)
    return f"wrote {len(text.splitlines())} line(s) to {path}"

def read_file(path):
    return Path(path).read_text()

claim = {"status": "incomplete", "progress": 0, "note": "not started"}

def report_status(status, progress, note=""):
    global claim
    claim = {"status": status, "progress": progress, "note": note}
    return f"noted: {status} at {progress}%"

TOOLS = {"write_file": write_file, "read_file": read_file,
         "report_status": report_status}

tool_schemas = [
    {
        "name": "write_file",
        "description": "Write text to a path, replacing whatever was there.",
        "input_schema": {
            "type": "object",
            "properties": {"path": {"type": "string"}, "text": {"type": "string"}},
            "required": ["path", "text"],
        },
    },
    {
        "name": "read_file",
        "description": "Read a file back and return its contents verbatim.",
        "input_schema": {
            "type": "object",
            "properties": {"path": {"type": "string"}},
            "required": ["path"],
        },
    },
    {
        "name": "report_status",
        "description": (
            "Report where you are against the goal. Call this after every write. "
            'Use "complete" only when notes/paris.md holds exactly three lines '
            "and you have read them back and seen all three."
        ),
        "input_schema": {
            "type": "object",
            "properties": {
                "status": {"type": "string", "enum": ["complete", "incomplete"]},
                "progress": {"type": "integer", "minimum": 0, "maximum": 100},
                "note": {"type": "string", "description": "one line: what is left"},
            },
            "required": ["status", "progress"],
        },
    },
]

# 2. the goal, in prose and in code
GOAL = ("Write notes/paris.md with exactly three lines about the weather, "
        "then read it back and confirm all three lines are there. "
        "Call report_status after every write.")

def goal_met():
    try:
        return len(NOTES.read_text().rstrip().splitlines()) == 3
    except FileNotFoundError:
        return False

def meter(p):                      # twenty cells, so each cell is 5%
    return f"[{'▓' * round(p / 5):·<20}] {p:3}%"

# 3. the loop
pool = ThreadPoolExecutor(max_workers=8)

def run_one(block):
    result = {"type": "tool_result", "tool_use_id": block.id}
    try:
        out = pool.submit(TOOLS[block.name], **block.input).result(TOOL_TIMEOUT_S)
        return {**result, "content": str(out)}
    except Timeout:
        return {**result, "is_error": True,
                "content": f"timed out after {TOOL_TIMEOUT_S}s"}
    except Exception as err:
        return {**result, "is_error": True, "content": str(err)}

messages = [{"role": "user", "content": GOAL}]
turn, nudges, budget, done = 0, 0, 16000, False

assert not goal_met(), "already done, nothing to run"

# one sentence saying what's missing, and the only place nudges are counted.
def nudge():
    global nudges
    nudges += 1
    if nudges > 1:
        raise RuntimeError("said done twice, the goal, the check or the tools disagree")
    text = ("notes/paris.md does not have three lines yet, you last reported "
            f"{claim['status']} at {claim['progress']}%. Finish the job.")
    claim["status"] = "incomplete"      # used up: make it report again
    return {"type": "text", "text": text}

while turn < MAX_TURNS:
    turn += 1
    reply = client.messages.create(
        model="claude-opus-5",
        max_tokens=budget,
        tools=tool_schemas,
        messages=messages,
    )

    # cut off: don't append a half-written tool call
    if reply.stop_reason == "max_tokens":
        budget = min(budget * 2, 64000)
        print(f"truncated, retrying with max_tokens {budget}")
        continue

    messages.append({"role": "assistant", "content": reply.content})

    # not an exit: a server-side tool paused part way. Send it all back unchanged.
    if reply.stop_reason == "pause_turn":
        continue

    if reply.stop_reason == "tool_use":
        calls = [b for b in reply.content if b.type == "tool_use"]
        results = [run_one(b) for b in calls]
        messages.append({"role": "user", "content": results})   # answer every call

        # the meter is a log line, never a test. Print it and watch it move.
        print(f"turn {turn}: {meter(claim['progress'])} {claim['note']}")

        # it said complete. Check the disk before believing it.
        if claim["status"] == "complete":
            if goal_met():
                done = True
                break
            results.append(nudge())   # `results` IS that message, so the nudge goes with it
        continue

    if reply.stop_reason != "end_turn":
        raise RuntimeError(f"unhandled stop_reason: {reply.stop_reason} "
                           f"{reply.stop_details}")

    # it stopped talking. If it never said complete, that's the "gave up"
    # case, and now it has a name in your log.
    if claim["status"] != "complete":
        print(f"end_turn at {claim['progress']}%")
    if goal_met():
        done = True
        break
    messages.append({"role": "user", "content": [nudge()]})

print(f"goal met in {turn} turn(s)" if done
      else f"stopped at the {MAX_TURNS}-turn cap, last claim {claim['status']} "
           f"at {claim['progress']}%, {claim['note']}")

One caveat on the Python version: it runs the tool on a pool thread and gives up on the result, not on the work. result(10) stops waiting, but the function keeps running in the background. That's honest, if untidy. So if a tool talks to the outside world, give it a real deadline of its own, timeout= on the HTTP call, statement_timeout on the database query, because giving up on a wait is not the same as cancelling a write.

When a tool hangs

Nothing in the API is watching a clock for you. Running the tools is your code, so if a tool never returns, your loop waits forever. This is the failure that looks like nothing at all: no error, no output, no bill, no end.

So give every tool a deadline, and treat a missed deadline as information, not as an exception. Send it back the normal way, in the normal place:

Retries are where good intentions cause damage. The rule: retry the connection, never the decision. A 429 or a dropped connection is worth trying again, twice, with a short wait in between, and the model never needs to hear about it. But a tool that ran fine and returned something you didn't like is not a retry. It's a result, and the model is the one who should decide what to do about it.

And before you retry anything that changes something, ask whether running it twice is safe. read_file is fine to repeat. send_email is not. If a tool writes, either make it idempotent, running it twice leaves the same result as running it once, or don't retry it at all, and let the model decide with the error in front of it.

Why the loop is the point, not the plumbing

The exits get all the attention in this lesson, so say the other half plainly: the loop isn't just plumbing for tool calls. The loop is what makes the answer better. A single request answers from the prompt alone. Turn 2 answers from the prompt plus what turn 1 found on disk. Turn 3 answers from both of those plus the mistake it just read back in its own tool_result. Every pass has more evidence than the one before it, so every pass can be better than the one before it.

That's why turn 3 of the transcript above wrote a third line. Nobody corrected the agent. It read two lines where it expected three, and fixed its own work. A single request can't do that at any model size, because there's no second look.

Which suggests the obvious next move: if one pass improves the work, run several on purpose. Just don't do it in one loop. A loop that writes and judges at the same time is grading its own homework, and it grades generously, because the conversation is full of its own reasoning about why the work is good. Use two loops instead.

Wrap the while loop you already wrote in a function: take the goal and the tool list as arguments, and instead of console.log at the end, return the last assistant text block. Then the two loops together are nine lines:

// runLoop(goal, tools) is the loop from above, returning its final text.
// The verify call has no goalMet() to satisfy, so it exits the normal way,
// on end_turn, which is exactly why that branch is still there.
const MAX_ROUNDS = 3;                    // same idea as MAX_TURNS, one level up
let notes = "";

for (let round = 1; round <= MAX_ROUNDS; round++) {
  await runLoop(`${GOAL}\n${notes}`, [writeTool, readTool]);   // improve: can write

  // verify: a new conversation, read-only tools, and one question.
  const report = await runLoop(
    `Read notes/paris.md. List every line that is not weather, or reply PASS.`,
    [readTool]);

  if (report.includes("PASS")) { console.log(`passed on round ${round}`); break; }
  notes = `A reviewer found these problems. Fix them:\n${report}`;
  console.log(`round ${round}: ${report}`);   // your record of what got better, and when
}

The catch: each round helps less than the last. Round 1 fixes the obvious problems, round 2 fixes what round 1 introduced, and round 3 usually rewrites phrasing you already liked. The cost doesn't taper off, though. Using the same math as before, priced at the caps: an improve loop that runs its full 12 turns is 43,200 input tokens, or $0.22, and a 4-turn verify loop on a fresh conversation is 4,800 tokens, or $0.02. One round of both is $0.24; three rounds is $0.72, 3× the bill for that second and third look. Worth it for a document people will read, wasteful for a log line. So cap the rounds, log which round passed, and after a week of logs you'll know whether round 3 ever earns its keep.

Straight about what we've shipped: the harness runs one loop, not two. There's no improve/verify button in the settings panel. You get two loops by writing them in your own script, which is why this is nine lines here and not a feature.

Let the model pace itself: task budgets

Your counter stops the loop from outside, and the model never sees it coming. It gets cut off mid-job with no chance to wrap up. Task budgets fix that. You give the model a token allowance for the whole run, it sees the countdown while it works, so it prioritises and finishes cleanly instead of being cut off. It's in beta, and it needs a header:

const reply = await client.beta.messages.create({
  betas: ["task-budgets-2026-03-13"],
  model: "claude-opus-5",
  max_tokens: 64000,
  output_config: {
    effort: "high",
    task_budget: { type: "tokens", total: 64000 },
  },
  tools: toolSchemas,
  messages,
});

Be clear about what you just bought. A task budget is a suggestion the model can see. max_tokens is a hard limit it can't see. And your turn counter is a hard stop on the number of round trips. Three different jobs, and the budget replaces neither of the others. Use all three, and definitely keep the counter, a budget the model can choose to overspend is not a cap.

The harness doesn't use task budgets. It counts steps, max steps, 40 by default in the settings panel, and stops there with a log line that tells you it was the setting and not the model: stopped after 40 steps (the max-steps setting). That's the cheap version, it's four lines, and it's the one to write first.

The trade-off: your counter vs. the SDK's

The tool runners from lesson 2 have a counter built in. In TypeScript, client.beta.messages.toolRunner({ ..., max_iterations: 12 }) is your MAX_TURNS, and the runner stops there. In Python you count inside for message in runner: and break, the same four lines you just wrote.

What the runner doesn't have is your goal. Nothing in the SDK knows that three lines is the job, so the check stays yours either way. Loop over the runner, and when a message comes back with stop_reason: "end_turn", run your check and add one more user message if it fails. Per-turn hooks are the place for an approval prompt, a log line, or a budget check.

So: use the runner for the loop, and keep the counter and the goal check yourself, because those are the two things a general-purpose helper can't guess. One more thing, check stop_reason on the final message even when the runner finished cleanly, because pause_turn comes back looking like success.

Seven rules for a loop that stops

  • Cap the turns, and log it when you hit the cap. A run that ends at the counter is not an answer. Print the number and the reason, or you'll go debugging the model when the real problem was a tool description.
  • Check the goal, don't trust the goodbye. end_turn says something about the model. Your check says something about the world. Only one of them is about the job.
  • Let it say “done” in a schema, not in prose. A report_status tool with a two-value enum turns “I think it's finished” into something your code can test. Log the progress number but never test it, it's a guess, and three flat readings in a row is your best stuck-agent alarm.
  • Nudge once. One sentence saying what's missing. If that doesn't work, stop and re-read your own prompt. A second nudge is just a loop with extra steps.
  • Give every tool a deadline. A hung tool is worse than a failing one, because nothing tells you. Send the timeout back as a tool_result with is_error: true.
  • Use two loops, don't make one longer. Each pass knows more than the last, so a second loop with read-only tools and no history is the cheapest quality you can buy. Cap the rounds too, and log which round passed.
  • Retry the connection, never the decision. Back off and retry on a 429 or a dropped socket. Everything else is a result the model should see, and anything that changes the world needs to be idempotent before you repeat it.

The exercise

Do this in the harness. It's the same loop, already running, with twenty-one tools on a virtual filesystem, and the counter from this lesson wired to the max steps box. Open KEYS, paste an API key or point it at Ollama, then ask for something that really does need several steps in order:

read notes/paris.md, add a fourth line with today's date, then read it back and tell me the line count

Watch the transcript for the same shape as the one above: a read, an edit, a second read, then prose. Three tool calls that had to happen in that order, and an agent that checked its own edit before saying it was done.

There's no report_status in the harness either. But ask for a five-step build and you'll see the todo tool go by in the transcript, doing the same trick, a status enum of pending/active/done, one per step, instead of one number for the whole run. The difference is that the harness only shows you that list; it doesn't make decisions from it. Your own loop should.

Then run the two loops by hand, as two requests, to feel the second look working. First ask it to improve notes/paris.md. Then send /clear, which empties the conversation and leaves the files alone, that's your fresh start. Now ask “read notes/paris.md and list every line that isn't weather, or reply PASS,” and read what the reviewer found. That list is exactly what round 2 of an improve loop would receive, and it's more specific than anything you'd have typed yourself. For the contrast, ask the same question without the /clear and watch it defend the draft it just wrote.

Then break it on purpose:

  • Set max steps to 2 and ask again. The run stops mid-job and says so. That's the cap working, and it's what your own MAX_TURNS log line should look like.
  • Give it a goal with no finish line, “keep improving notes/paris.md”, and watch how long it keeps going. That's the argument for checkable goals, in one run.
  • Turn off read_file in TOOLS and ask it to verify an edit. It can't check, so watch whether it admits that or claims success anyway. Then decide which of those two behaviours you'd ship.
  • In your own script, set the model up to claim complete when it isn't: ask for three lines in the prompt, but have goalMet() look for four. It will report complete at 100%, twice, and then your nudge limit fires. That error message is the one you want.

All four are safe to run. The harness writes to a virtual filesystem in localStorage in your own tab, so nothing here touches your real disk. /wipe clears the workspace, and /undo rewinds both the files and the conversation until you close the tab. The runaway you cause on purpose costs cents, the cheapest possible way to meet one.

That's why this lesson came first. Every one of those is a stopping problem, and you now have a counter, a deadline and a goal check to bring with you. An agent that reaches the network without them doesn't fail loudly. It just waits.

An agent that stops on purpose is one you can leave running on someone else's behalf, which is the only reason anyone hands one real work.
