Lesson 6: evals - make "seems better" prove it

You made it to lesson six, the last one. I'm glad you're here. Over the past few weeks, we've given a model tools, put it in a loop, added memory, and taught it to see. Now we get to ask the awkward question: did any of it actually help?

Sometimes a small change looks like it fixed everything, but a few good results can just be luck. In this final lesson, we'll test it properly: 10 cases, 3 runs each, and code that grades all 30 results. That way, we'll know whether the change really helped.

Five good runs might mean nothing

A model can answer the same prompt differently from run to run. You edit a description, try the agent five times, and get four good answers. Nice! Except the old version might also have passed four times. Until you test both, you're comparing a result with a hunch.

A small eval gives you a fair comparison: a list of prompts, a function that scores each run, and a loop that prints the total. Ours fits in one file. No eval platform, no dashboard, no new hobby maintaining the dashboard.

Our willing test subject

Our test subject is a support agent with three tools. Stub functions return canned data, so the agent can make a complete mess without touching a real order or refunding anyone's money. Very freeing.

  • lookup_order(order_id) returns the requested order's status.
  • search_orders(email) returns order ids for a customer.
  • refund_order(order_id) moves money, so choosing it by mistake is expensive.

The grader looks for old enemies from earlier lessons: searching when the user already supplied an order id, inventing an id, or treating an angry complaint as permission to move money. The recorded tool calls give plain old code everything it needs to catch them.

Grade with code first

Use the simplest grader that can answer the question. Boring is good here.

  • Use code on the trace when the verdict depends on which tools ran, their order, or their arguments. The check is fast and returns the same verdict every time. Lesson 3's DOM check worked this way.
  • Use code on the end state when a file should exist, a test should pass, or a database row should change.
  • Use a model as judge for prose that a function cannot grade. Judge calls cost tokens and can make grading errors.

Give each run a pass or fail. A tone score of 7 out of 10 sounds useful until you have to explain why the next answer got an 8. A yes-or-no check is easier to defend, and you can count it without squinting.

Ten cases

Write the cases before you edit the prompts. Otherwise, it's too easy to write tests that flatter the change you just made. Each case pairs a user message with a function that reads the recorded tool calls and returns true or false. Some cases should expect no tool call at all. A useful agent knows when to stop and ask for what it needs.

Failures make excellent cases. When the agent finds a new and creative way to be wrong, save the prompt as case 11. Add a few troublemakers of your own, especially around costly or irreversible tools. Today's weird bug is tomorrow's very useful test.

Run each case more than once

One pass proves exactly one pass. To see whether an improvement holds up, run each case 3 times. That gives you 30 runs, and each run takes about two requests of 1,000 input tokens. Budget roughly 60,000 input tokens for the whole eval and check usage on your first run for the actual figure.

Suppose the agent passes 80% of its runs. With 30 runs, the standard error is √(0.8 × 0.2 ÷ 30), which is about 7 points. A move from 80% to 86% fits inside that noise. At 90 runs, the error drops to about 4 points while the token cost triples.

Use the total to spot broad changes and the traces to explain individual failures:

  • Ignore a change of only a couple of passes out of 30.
  • Open the trace when a case falls from 3/3 to 0/3. A change that sharp points to a specific regression.
  • Rerun a total that moves by 15 points or more. A repeat is cheap confirmation of a change that large.

Two sets of descriptions

The eval compares two sets of tool descriptions. Variant A contains the short, vague descriptions we've all written while trying to get something working before lunch. Variant B says when to use each tool, what input it needs, and which requests to reject.

Keep the system prompt, model, stubs, and cases fixed. Change one thing per eval run. If you change the description and the model together, a better score leaves you with a mystery. The agent improved. Great. You just don't know why.

JavaScript example

Run it with VARIANT=A node eval.mjs, then VARIANT=B node eval.mjs.

# once
npm install @anthropic-ai/sdk
import Anthropic from "@anthropic-ai/sdk";
import { mkdir, writeFile } from "node:fs/promises";

const client = new Anthropic();
const MODEL = process.env.MODEL ?? "claude-opus-5-5";
const VARIANT = process.env.VARIANT ?? "A";
const RUNS = 3;          // samples per case; see the arithmetic above
const MAX_TURNS = 6;     // lesson 3's cap, so a bad run can't hang the eval

const SYSTEM = "You are a support agent for a shop. Use the tools. If a tool needs " +
               "something the customer hasn't told you, ask for it.";

// The only thing we change between runs.
const DESCRIPTIONS = {
  A: {
    lookup_order: "Look up an order.",
    search_orders: "Search orders.",
    refund_order: "Refund an order.",
  },
  B: {
    lookup_order: "Get the status and total of an order when you already have its order id " +
                  "(like A-1042). Never guess an id.",
    search_orders: "Find a customer's orders by email when they gave no order id. Returns " +
                   "ids and dates, not statuses; call lookup_order for those.",
    refund_order: "Refund an order in full. Only when the customer explicitly asks for a " +
                  "refund; a complaint is not a request. Money moves and cannot be undone.",
  },
};

const d = DESCRIPTIONS[VARIANT];
const TOOLS = [
  { name: "lookup_order", description: d.lookup_order,
    input_schema: { type: "object", properties: { order_id: { type: "string" } }, required: ["order_id"] } },
  { name: "search_orders", description: d.search_orders,
    input_schema: { type: "object", properties: { email: { type: "string" } }, required: ["email"] } },
  { name: "refund_order", description: d.refund_order,
    input_schema: { type: "object", properties: { order_id: { type: "string" } }, required: ["order_id"] } },
];

// Stubs: canned answers, no side effects. Nothing is ever refunded.
const STUBS = {
  lookup_order: ({ order_id }) => ({ id: order_id, status: "shipped", total: "$42.00" }),
  search_orders: () => ({ orders: [{ id: "A-1042", date: "2026-09-30" }] }),
  refund_order: () => ({ refunded: true }),
};

// Graders read the trace: [{ name, input }, ...] in the order the calls happened.
const names = (calls) => calls.map((c) => c.name);
const first = (calls) => calls[0];

const CASES = [
  { id: "status by id", prompt: "Where is order A-1042?",
    pass: (c) => first(c)?.name === "lookup_order" && first(c).input.order_id === "A-1042" },
  { id: "status by email", prompt: "What's the status of my order? sam@example.com",
    pass: (c) => first(c)?.name === "search_orders" && first(c).input.email === "sam@example.com" },
  { id: "complaint is not a refund", prompt: "Order A-1042 arrived broken. Unacceptable.",
    pass: (c) => !names(c).includes("refund_order") },
  { id: "explicit refund", prompt: "Please refund order A-1042, it arrived broken.",
    pass: (c) => c.some((x) => x.name === "refund_order" && x.input.order_id === "A-1042") },
  { id: "search then refund", prompt: "Refund my last order. sam@example.com",
    pass: (c) => names(c).indexOf("search_orders") !== -1 &&
                 names(c).indexOf("search_orders") < names(c).indexOf("refund_order") &&
                 c.some((x) => x.name === "refund_order" && x.input.order_id === "A-1042") },
  { id: "price by id", prompt: "How much did order B-2210 cost?",
    pass: (c) => first(c)?.name === "lookup_order" && first(c).input.order_id === "B-2210" },
  { id: "no tool needed", prompt: "Thanks, that's all!",
    pass: (c) => c.length === 0 },
  { id: "asks, doesn't guess", prompt: "Where is my order?",
    pass: (c) => c.length === 0 },
  { id: "no cancel tool", prompt: "Cancel order A-1042.",
    pass: (c) => !names(c).includes("refund_order") },
  { id: "search then lookup", prompt: "Is the latest order for alex@example.com shipped?",
    pass: (c) => names(c).indexOf("search_orders") !== -1 &&
                 names(c).indexOf("search_orders") < names(c).indexOf("lookup_order") },
];

// A single run for a case. Returns the tool calls it made.
async function runOnce(prompt) {
  const calls = [];
  const messages = [{ role: "user", content: prompt }];
  for (let turn = 1; turn <= MAX_TURNS; turn++) {
    const reply = await client.messages.create({
      model: MODEL, max_tokens: 1024, system: SYSTEM, tools: TOOLS, messages,
    });
    messages.push({ role: "assistant", content: reply.content });
    if (reply.stop_reason !== "tool_use") return { calls };

    const results = [];
    for (const use of reply.content.filter((b) => b.type === "tool_use")) {
      calls.push({ name: use.name, input: use.input });
      results.push({ type: "tool_result", tool_use_id: use.id,
                     content: JSON.stringify(STUBS[use.name](use.input)) });
    }
    messages.push({ role: "user", content: results });
  }
  return { calls, capped: true };     // hit the turn cap, so the run failed
}

async function runCase(c) {
  const runs = [];
  for (let i = 0; i < RUNS; i++) {
    try {
      const { calls, capped } = await runOnce(c.prompt);
      runs.push({ pass: !capped && c.pass(calls), calls });
    } catch (err) {
      // Keep API errors separate from wrong answers.
      runs.push({ pass: false, error: String(err.message ?? err) });
    }
  }
  return { id: c.id, runs };
}

const results = await Promise.all(CASES.map(runCase));   // cases in parallel, runs in series

let passed = 0, errors = 0;
for (const r of results) {
  const marks = r.runs.map((x) => (x.error ? "!" : x.pass ? "+" : "-")).join("");
  passed += r.runs.filter((x) => x.pass).length;
  errors += r.runs.filter((x) => x.error).length;
  console.log(`${marks}  ${r.id}`);
}
const total = CASES.length * RUNS;
console.log(`\nvariant ${VARIANT} on ${MODEL}: ${passed}/${total} (${Math.round(100 * passed / total)}%)` +
            (errors ? `, ${errors} API errors, rerun before you trust it` : ""));

await mkdir("evals", { recursive: true });
await writeFile(`evals/${VARIANT}.json`, JSON.stringify({ MODEL, VARIANT, results }, null, 2));

Each line reports a case. A plus means pass, a minus means fail, and a bang means API error. A line such as +-- exposes an unstable case that the total can hide. The script also writes every tool call to evals/A.json or evals/B.json for later inspection.

Python example

The Python version uses a thread pool to run the cases in parallel:

# once
pip install anthropic
import json
import os
from concurrent.futures import ThreadPoolExecutor
from pathlib import Path

import anthropic

client = anthropic.Anthropic()
MODEL = os.environ.get("MODEL", "claude-opus-5-5")
VARIANT = os.environ.get("VARIANT", "A")
RUNS = 3          # samples per case; see the arithmetic above
MAX_TURNS = 6     # lesson 3's cap, so a bad run can't hang the eval

SYSTEM = ("You are a support agent for a shop. Use the tools. If a tool needs "
          "something the customer hasn't told you, ask for it.")

# The only thing we change between runs.
DESCRIPTIONS = {
    "A": {
        "lookup_order": "Look up an order.",
        "search_orders": "Search orders.",
        "refund_order": "Refund an order.",
    },
    "B": {
        "lookup_order": "Get the status and total of an order when you already have its order id "
                        "(like A-1042). Never guess an id.",
        "search_orders": "Find a customer's orders by email when they gave no order id. Returns "
                         "ids and dates, not statuses; call lookup_order for those.",
        "refund_order": "Refund an order in full. Only when the customer explicitly asks for a "
                        "refund; a complaint is not a request. Money moves and cannot be undone.",
    },
}

d = DESCRIPTIONS[VARIANT]
TOOLS = [
    {"name": "lookup_order", "description": d["lookup_order"],
     "input_schema": {"type": "object", "properties": {"order_id": {"type": "string"}}, "required": ["order_id"]}},
    {"name": "search_orders", "description": d["search_orders"],
     "input_schema": {"type": "object", "properties": {"email": {"type": "string"}}, "required": ["email"]}},
    {"name": "refund_order", "description": d["refund_order"],
     "input_schema": {"type": "object", "properties": {"order_id": {"type": "string"}}, "required": ["order_id"]}},
]

# Stubs: canned answers, no side effects. Nothing is ever refunded.
STUBS = {
    "lookup_order": lambda i: {"id": i["order_id"], "status": "shipped", "total": "$42.00"},
    "search_orders": lambda i: {"orders": [{"id": "A-1042", "date": "2026-09-30"}]},
    "refund_order": lambda i: {"refunded": True},
}


# Graders read the trace: [{"name": ..., "input": {...}}, ...] in call order.
def names(calls):
    return [c["name"] for c in calls]


def first_is(calls, name, **expect):
    return bool(calls) and calls[0]["name"] == name and \
        all(calls[0]["input"].get(k) == v for k, v in expect.items())


def before(calls, a, b):
    n = names(calls)
    return a in n and b in n and n.index(a) < n.index(b)


CASES = [
    ("status by id", "Where is order A-1042?",
     lambda c: first_is(c, "lookup_order", order_id="A-1042")),
    ("status by email", "What's the status of my order? sam@example.com",
     lambda c: first_is(c, "search_orders", email="sam@example.com")),
    ("complaint is not a refund", "Order A-1042 arrived broken. Unacceptable.",
     lambda c: "refund_order" not in names(c)),
    ("explicit refund", "Please refund order A-1042, it arrived broken.",
     lambda c: any(x["name"] == "refund_order" and x["input"].get("order_id") == "A-1042" for x in c)),
    ("search then refund", "Refund my last order. sam@example.com",
     lambda c: before(c, "search_orders", "refund_order") and
               any(x["name"] == "refund_order" and x["input"].get("order_id") == "A-1042" for x in c)),
    ("price by id", "How much did order B-2210 cost?",
     lambda c: first_is(c, "lookup_order", order_id="B-2210")),
    ("no tool needed", "Thanks, that's all!",
     lambda c: len(c) == 0),
    ("asks, doesn't guess", "Where is my order?",
     lambda c: len(c) == 0),
    ("no cancel tool", "Cancel order A-1042.",
     lambda c: "refund_order" not in names(c)),
    ("search then lookup", "Is the latest order for alex@example.com shipped?",
     lambda c: before(c, "search_orders", "lookup_order")),
]


def run_once(prompt):
    """A single run for a case. Returns (calls, capped)."""
    calls = []
    messages = [{"role": "user", "content": prompt}]
    for _ in range(MAX_TURNS):
        reply = client.messages.create(
            model=MODEL, max_tokens=1024, system=SYSTEM, tools=TOOLS, messages=messages,
        )
        messages.append({"role": "assistant", "content": reply.content})
        if reply.stop_reason != "tool_use":
            return calls, False

        results = []
        for use in (b for b in reply.content if b.type == "tool_use"):
            calls.append({"name": use.name, "input": use.input})
            results.append({"type": "tool_result", "tool_use_id": use.id,
                            "content": json.dumps(STUBS[use.name](use.input))})
        messages.append({"role": "user", "content": results})
    return calls, True     # hit the turn cap, so the run failed


def run_case(case):
    case_id, prompt, check = case
    runs = []
    for _ in range(RUNS):
        try:
            calls, capped = run_once(prompt)
            runs.append({"pass": (not capped) and check(calls), "calls": calls})
        except Exception as err:
            # Keep API errors separate from wrong answers.
            runs.append({"pass": False, "error": str(err)})
    return {"id": case_id, "runs": runs}


with ThreadPoolExecutor(max_workers=len(CASES)) as pool:     # cases in parallel, runs in series
    results = list(pool.map(run_case, CASES))

passed = errors = 0
for r in results:
    marks = "".join("!" if x.get("error") else "+" if x["pass"] else "-" for x in r["runs"])
    passed += sum(x["pass"] for x in r["runs"])
    errors += sum("error" in x for x in r["runs"])
    print(f"{marks}  {r['id']}")

total = len(CASES) * RUNS
print(f"\nvariant {VARIANT} on {MODEL}: {passed}/{total} ({round(100 * passed / total)}%)"
      + (f", {errors} API errors, rerun before you trust it" if errors else ""))

Path("evals").mkdir(exist_ok=True)
Path(f"evals/{VARIANT}.json").write_text(json.dumps(
    {"MODEL": MODEL, "VARIANT": VARIANT, "results": results}, indent=2, default=str))

I left out scores for A and B on purpose. They vary by model and by run, and my total would tell you very little about your agent. Run both variants and keep the traces with your code. Your own repeatable result is the one that matters.

Read the trace before you trust the number

Open evals/A.json and inspect a failing run. The agent may have made a bad decision, or the grader may have rejected a valid choice.

  • If the agent chose the wrong tool or argument, fix the description or prompt and rerun.
  • If the grader rejected acceptable behavior, fix the grader. Case 8, for example, passes when the model asks for an email without calling a tool. A call to search_orders with an empty string should fail. An exact-string check for the model's reply would be too strict and would reject many valid questions.

Read five failures by hand the first time you run a new eval. Sometimes the grader is wrong and the agent is fine. Finding that early can save you an afternoon of fixing the wrong thing, which is a lovely way to get an afternoon back.

When you need a model as judge

Code cannot decide whether a reply sounds polite or a summary preserves an important fact. For those cases, send the output to a second model call and ask for pass or fail against a short rubric.

const verdict = await client.messages.create({
  model: "claude-opus-5-5",
  max_tokens: 200,
  messages: [{ role: "user", content:
    `Rubric: the reply apologizes once, offers a next step, and does not promise a refund.\n\n` +
    `Reply:\n${reply}\n\n` +
    `Think briefly, then end with exactly PASS or FAIL.` }],
});
const ok = verdict.content[0].text.trim().endsWith("PASS");

Test the judge's verdicts against your own before you rely on it:

  • Label 20 outputs yourself, then run the judge on the same set. If it disagrees on more than two or three, fix the rubric before using it on anything else.
  • Ask a narrow yes/no question per judge call. "Is this good?" is vague. "Does it promise a refund?" gives the judge a clear job.
  • Grade with a separate call and rubric. A different model can reduce shared blind spots between the agent and judge.
  • Keep code graders for facts code can inspect. Case 3 asks whether the agent called the refund tool, which is visible in the trace and needs no judge.

Avoid overfitting your own cases

After a week of tuning against the same ten cases, you can end up with descriptions that ace those prompts and fall apart everywhere else. The score keeps climbing while unfamiliar requests remain just as hard. Sneaky.

Write 15 cases, tune against ten, and leave five untouched until you're ready to decide. If only the tuning set improves, you are probably overfitting. Move any useful held-out failure into the tuning set and replace it with a new case.

Now test the whole little machine

Lesson 1 put a model in the browser. Lesson 2 gave it tools. Then you added loops, memory, and vision. The eval gives you a way to revisit all of those choices. Keep the parts that improve the score or make failures easier to understand.

  • Try a cheaper model with MODEL=claude-haiku-4-5-20251001 VARIANT=B node eval.mjs. If it scores within noise of the larger model on your ten cases, you can cut the bill on this task. A drop on refusal cases tells you where the cheaper model needs help.
  • Compare longer descriptions. B adds input tokens to every request; its score shows whether those words earn their cost.
  • Rerun the eval after a model upgrade so you catch regressions before users do.

Build the eval you'll actually run again

A suite can take a few minutes, cost a few dollars, and run after every prompt or tool change. Commit the evals/*.json files beside the code so each diff shows which case results changed after an edit.

This example skips CI. Run it by hand at first. If you keep forgetting, congratulations: you've found the moment to automate it.

Eval checklist

  • Write the cases and graders before you change the prompt.
  • Grade the trace or end state with code. Reserve a judge for output that code cannot assess.
  • Pass or fail. No 1 to 10 scores.
  • Include cases where the right move is to do nothing, or to ask.
  • Run each case at least 3 times, and know your error bar: √(p × (1 − p) ÷ runs).
  • Change a single thing between runs: a description, a prompt, or a model.
  • Record API errors separately from failed cases.
  • Read a handful of failing traces by hand to check the grader.
  • Turn every failure you encounter into a new case.
  • Hold some cases out so you can tell improvement from memorization.
  • Keep the turn cap from lesson 3 in the eval loop.

Your last exercise

  1. Copy the JavaScript or Python file above and run it with VARIANT=A, then VARIANT=B. Write both totals down. Compare the per-case marks, not only the totals.
  2. Run variant A a second time. The gap between its two totals is your noise. Judge every later change against it.
  3. Open the trace for a failing case in A and change a sentence in its description to fix it. Rerun and check that case as well as the other nine for regressions.
  4. Add a case 11 that you expect to fail: a prompt that makes your agent do something you don't want. Make it pass without breaking the other ten.
  5. Set MODEL to a smaller model and run B. Decide from the numbers whether it is good enough for this task.

You can paste any case into the harness and watch its tool calls in the transcript. Use the file above to calculate a pass rate, then replay individual failures in the harness. For the last lab, measure the agent, pick one failed case, and make it pass.
