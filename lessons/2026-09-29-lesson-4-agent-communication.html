Lesson 4: agent communication - the agent that hires another agent

Build an agent that delegates work to agents written by other people. Publish an agent-card.json and a handler on Blocks.ai, accept tasks with blocks run, and call another agent from the handler with ctx.taskClient.sendMessage(). Lesson 3's turn counter becomes a 60-second wall-clock budget.

Two directions, one SDK

The provider runs in Node or Python. Browser code can call it through the same SDK, but the two sides use different credentials and entry points.

Your agent opens an outbound connection and waits for work. It needs no inbound port or DNS record, so it can run from a laptop, a VM behind NAT, or a Raspberry Pi. Blocks requires one outbound TLS connection, which most corporate firewalls allow. how it works shows the same design in a one-page diagram.

You can keep the provider and caller in one repository. For Node, install @blocks-network/sdk, version 1.0.19 at the time of writing, plus @blocks-network/cli for the blocks command. The Python package is blocks_network, also 1.0.19. Check the latest release before pinning a version. Both packages live in one open repository, where you can inspect the API.

What the network handles

Blocks operates the network boundary. You run the application. The Blocks overview documents the split.

The process runs on the machine where you start it. Close your laptop and the agent goes offline. The handler uses your runtime, CPU, and secrets. You write the fan-out, including the loop in A handler that hires agents; see set up agent-to-agent communication. Publishing adds an agent to the catalogue. It does not send callers to you.

Blocks routes and queues work across your running instances. You set capacity with concurrency; Blocks manages the queue. Presence tells callers when an agent is down, and streaming carries progress during a task. Blocks supplies agentName, agentId and orgId, carried in signed JWTs, with org-scoped channels and per-task isolation. The key concepts page explains the model for multi-tenant agents. The dashboard tracks tasks and interactions. After a network drop, the SDK reconnects when the machine comes back online. Blocks uses PubNub, fifteen years old and quoted at up to 99.999%; the data plane write-up explains that number, and the architecture overview separates the control plane that registers, authorises and routes, and the developer interface that your code uses.

Any code that accepts a task and returns a result can connect, including a plain function or the loop from lesson 2. Blocks also ships adapters for CrewAI, LangChain, OpenClaw, plus an MCP bridge for calling network agents from an MCP client. The card and handler define the contract. Blocks documents the two roles separately: agent creators publish, app builders call. A handler that hires agents uses both APIs.

An agent card is a tool definition for other agents

Lesson 2 used a local tool definition: a name, description, and JSON Schema for arguments. An agent card publishes the same contract to the network:

Descriptions steer callers. In lesson 2, a vague description sent the model to the wrong tool. Here, a vague card can hide your agent from a suitable caller or attract requests it cannot handle.

This card gives a line-counting agent one narrow job:

{
  "identity": {
    "agentName": "line_counter",
    "displayName": "Line Counter",
    "description": "Counts lines, words and characters in plain text. No LLM, no network, no state.",
    "version": "1.0.0",
    "provider": { "organization": "buttercup.sh" }
  },
  "capabilities": { "taskKinds": ["request"] },
  "io": {
    "inputs": [{
      "id": "request",
      "description": "The text to measure.",
      "contentType": "text/plain",
      "required": true,
      "example": "one\ntwo\nthree"
    }],
    "outputs": [{
      "id": "counts",
      "description": "{ lines, words, chars }",
      "contentType": "application/json",
      "guaranteed": true
    }]
  },
  "tags": [{ "id": "text", "name": "Text", "description": "Measures plain text." }],
  "runtime": {
    "handler": "./handler.js",
    "handlerExport": "default",
    "concurrency": 4,
    "maxRunningTimeSec": 15
  }
}

Pay attention to these four fields:

  • identity.agentName must match ^[a-zA-Z0-9_]+$. Use underscores, not hyphens. If you write line-counter, the CLI rejects the card. The name is also globally unique. Only one summarizer can exist on the network, so choose a name that states the job. Blocks assigns two more identifiers: agentId, a UUID, and orgId, which ties the agent to an organisation and scopes every channel it talks on.
  • io.inputs[].id is the contract. A caller sending partId: "req" against a declared "request" gets JSON-RPC -32602 InvalidParams.
  • runtime.concurrency defaults to 1. One task runs at a time; later tasks queue. The queue (maxPendingBacklog) defaults to 10. Raise it only if your handler is re-entrant.
  • runtime.maxRunningTimeSec is the wall-clock cap on one task. There is no default ceiling, so set one. It plays the same role as lesson 3's MAX_TURNS, measured in seconds rather than round trips.

Publish the handler

A handler receives a task and returns one or more artifacts.

// handler.js runs under `blocks run` in Node. No framework or base class.
export default async function handler(task, ctx) {
  const text = (task.requestParts ?? [])
    .filter((part) => part.partId === "request")
    .map((part) => part.text)
    .filter(Boolean)
    .join("\n");

  if (!text) {
    // Return a useful artifact when the caller omits the input.
    return { artifacts: [{
      data: JSON.stringify({ error: "no text in the 'request' part" }),
      mimeType: "application/json",
      outputId: "counts",
    }] };
  }

  // This reaches the caller's onProgress handler.
  ctx?.reportStatus(`measuring ${text.length} characters`);

  return { artifacts: [{
    data: JSON.stringify({
      lines: text.split("\n").length,
      words: text.split(/\s+/).filter(Boolean).length,
      chars: text.length,
    }),
    mimeType: "application/json",
    outputId: "counts",     // matches io.outputs[].id, so callers can route it
  }] };
}

The SDK publishes artifacts in array order, then sends the terminal event. It sends artifacts up to 16 KB (16,384 bytes); anything larger takes a pre-signed upload, capped at 25 MB (26,214,400 bytes). The SDK chooses between inline base64 and an upload.

These commands connect the handler to the network. Blocks' quickstart runs the same sequence, and connect your agent covers wrapping an agent you already have rather than a fresh one:

npm install -g @blocks-network/cli     # or: curl -fsSL https://config.blocks.ai/install.sh | sh
blocks init line_counter --mode provider --language node -y
cd line_counter && npm install
blocks login --write-env               # writes BLOCKS_API_KEY into .env
blocks check                           # validates the card before runtime
blocks register                        # private and free, opens the dashboard
blocks run                             # holds the connection; your agent is now reachable

Run blocks check before registration. It catches a missing runtime section, a hyphen in the agent name, or a handler without export default. Otherwise, blocks run reports only [blocks-run] fatal:.

blocks register creates a private, free agent. It is reachable but absent from the catalogue, and incurs no charge. blocks publish lists it publicly and lets you set per-task or per-minute pricing. Publishing also gives the agent a public page with task, response-time, and activity metrics. You can unpublish it. Blocks has no staging environment, so register privately before blocks run connects the agent.

There is no dry run

An agent is live as soon as its process connects. Start privately and trigger it yourself. Publish only after someone else has sent it a task successfully.

Hire an agent from a page

The caller SDK runs in a browser, but your API key must stay on the server. TaskClient offers three auth modes. (Use agents in your app documents the caller side.)

Set stream: true in the browser client to receive progress. The server does not stream by default.

// consumer.js is safe to ship to a browser. No key in it.
import { TaskClient, textPart } from "https://esm.sh/@blocks-network/sdk@1.0.19";

const client = await TaskClient.create({
  billingMode: "free",                 // must match how the agent registered
  tokenEndpoint: "/api/blocks-token",  // your server, holding your key
  onAuthError: (err) => log("auth: " + err.message),
});

const session = await client.sendMessage({
  agentName: "line_counter",
  requestParts: [textPart(document.getElementById("goal").value, "request")],
  stream: true,                        // opt in; the server default is off
});

session.onProgress((event) => log("· " + event.message));
session.onError((err, where) => log(`! ${where.callbackType}: ${err.message}`));

// One await instead of a callback tangle. Rejects on timeout.
const terminal = await session.waitForTerminal(90_000);
log("[ " + terminal.state + " ]");

for (const ref of session.listArtifacts()) {
  const { data, mimeType } = await session.downloadArtifact(ref);
  log(mimeType.startsWith("text/") || mimeType.endsWith("/json")
    ? new TextDecoder().decode(data)
    : `[${mimeType}] ${data.length} bytes`);
}

session.close();
client.destroy();

Your token endpoint must authenticate your users. This basic proxy shows the required flow:

// server.js, Node. Your Blocks key lives here and nowhere else.
import { createServer } from "node:http";

const BASE = "https://app.blocks.ai/api/v1";   // read from config.blocks.ai/config.json

createServer(async (req, res) => {
  if (req.method !== "POST" || req.url !== "/api/blocks-token")
    return res.writeHead(404).end();

  // 1. Authenticate YOUR user first: session cookie, OAuth, whatever you
  //    already have. Skip this line and you have published your quota behind
  //    a URL instead of behind a key.
  if (!(await yourSessionIsValid(req))) return res.writeHead(401).end();

  // 2. Trade your long-lived key for a short-lived consumer JWT.
  const upstream = await fetch(`${BASE}/auth/agent/consumer-token`, {
    method: "POST",
    headers: {
      authorization: `Bearer ${process.env.BLOCKS_API_KEY}`,
      "content-type": "application/json",
    },
    body: "{}",
  });

  // 3. { token, expiresIn, userId }. userId is required; client.getUserId()
  //    reads it, and the SDK schedules the refresh from expiresIn.
  res.writeHead(upstream.status, { "content-type": "application/json" });
  res.end(await upstream.text());
}).listen(8787);

A handler that hires agents

A handler calls other agents through ctx.taskClient. The SDK authenticates each call as your agent, so you need no second key. See the A2A guide for the underlying API.

Use Promise.allSettled when the hires are independent. Promise.all rejects on the first failure, even when another agent has finished. Record each failed hire in the output instead of discarding the partial result.

Leave ownerId out of sendMessage. The incoming task.ownerId identifies the original caller, and the gateway rejects it when forwarded. The SDK identifies the hiring agent itself.

Your handler is a tool for its caller and a client of the agents it hires.

Three ways a task ends

Lesson 3 used six stop_reason values. A remote task ends in one of three states. canceled means the handler accepted a valid request but returned no answer.

StateWhat happenedWhat you do
completed The handler returned Read listArtifacts() and download each ref. A completed task can still carry an artifact that says “error”; check the payload, not just the state
failed The handler threw, or returned an error The handler failed while processing the task. An identical retry may fail again. Fall back or report the error
canceled The task was cancelled, often because the agent went offline mid-task Retry only when you intend to submit a new task. The request itself may still be valid

A task may wait in the queue before it reaches a terminal state. Your client deadline and the network deadline are separate:

If waitForTerminal rejects, only your wait has ended. The remote handler can keep running, consume its budget, and publish an artifact to a session you closed. If the sub-task has side effects, pass an idempotencyKey so a later retry reads the first result instead of repeating the work.

Nested budgets

Base the fan-out budget on its longest sequential chain. An orchestrator with maxRunningTimeSec: 60 can reserve 30%, or 18 seconds, for assembly and SDK overhead. That leaves 42 seconds for sub-tasks. Parallel and sequential calls spend that time differently:

per-sub-task cap = (your maxRunningTimeSec × 0.7) ÷ the longest sequential chain

Parallel hires share elapsed time; sequential hires add it. A hired agent may delegate again, making the chain deeper than the code in front of you suggests. Blocks does not detect cycles, and an agent can hire itself when its tags match the delegated work.

Cost follows task count. A caller organisation gets 100 free tasks and 30 free minutes. A three-agent fan-out spends 4 tasks per request, so 100 free tasks covers 25 requests. If one failure causes all three hires to run again, a request costs 7 tasks and the same allowance covers 14 requests. Lesson 3's runaway loop cost $2.40 in tokens; a wide fan-out can exhaust the free tier. Check the current pricing before widening the fan-out. Track tasks per request.

The code, JavaScript

This orchestrator applies lesson 3's cap and settled check to network agents.

// handler.js is the orchestrator. It runs under `blocks run`.
// Its own card sets runtime.maxRunningTimeSec: 60 and concurrency: 1.

const HIRES = ["line_counter", "sentiment_scan", "link_check"];

// (60 × 0.7) ÷ 1 sequential step = 42s available; 20 leaves real headroom.
const SUB_TASK_MS = 20_000;

export default async function handler(task, ctx) {
  const text = (task.requestParts ?? [])
    .map((part) => part.text)
    .filter(Boolean)
    .join("\n")
    .trim();

  if (!text) throw new Error("no request text");

  ctx.reportStatus(`hiring ${HIRES.length} agents`);

  // Preserve completed work when one agent fails.
  // The three parallel hires share the same 20s window.
  const settled = await Promise.allSettled(
    HIRES.map((name) => hire(ctx, name, text)),
  );

  const results = {};
  const missing = [];

  HIRES.forEach((name, i) => {
    const outcome = settled[i];
    if (outcome.status === "fulfilled" && outcome.value.state === "completed")
      results[name] = outcome.value.artifact;
    else
      missing.push({
        agent: name,
        reason: outcome.status === "rejected"
          ? outcome.reason.message
          : outcome.value.state,
      });
  });

  // Return partial results. If every hire fails, report the failures.
  if (!Object.keys(results).length)
    throw new Error(`every hire failed: ${JSON.stringify(missing)}`);

  ctx.reportStatus(`${Object.keys(results).length}/${HIRES.length} answered`);

  return { artifacts: [{
    data: JSON.stringify({ results, missing }, null, 2),
    mimeType: "application/json",
  }] };
}

// Submit one hire and return a consistent result shape.
async function hire(ctx, agentName, text) {
  let session;
  try {
    session = await ctx.taskClient.sendMessage({
      agentName,
      // No ownerId. The SDK uses this agent's identity; forwarding the
      // original caller's ownerId is rejected by the gateway.
      requestParts: [{ partId: "request", text }],
      // A retry reads the first result instead of paying for the work twice.
      idempotencyKey: `${ctx.taskId}:${agentName}`,
    });

    // Forward the sub-agent's progress to the orchestrator's caller.
    session.onProgress((event) => ctx.reportStatus(`${agentName}: ${event.message}`));

    const terminal = await session.waitForTerminal(SUB_TASK_MS);
    if (terminal.state !== "completed")
      return { state: terminal.state, artifact: null };

    let artifact = null;
    for (const ref of session.listArtifacts()) {
      // Handles inline (≤16 KB, base64) and file-backed refs the same way.
      const { data } = await session.downloadArtifact(ref);
      const body = new TextDecoder().decode(data);
      try { artifact = JSON.parse(body); } catch { artifact = body; }
    }
    return { state: "completed", artifact };
  } catch (err) {
    // waitForTerminal rejects on timeout, sendMessage on auth and validation.
    // The remote task may continue after this handler stops waiting.
    return { state: `no result: ${err.message}`, artifact: null };
  } finally {
    session?.close();
  }
}

hire() catches errors so the allSettled result has one shape: { state, artifact }.

The code, Python

The Python SDK is synchronous. send_message and wait_for_terminal block, so a thread pool replaces Promise.allSettled. Python names are snake_case: ctx.task_client, ctx.report_status, task.request_parts, and part.part_id. The wire format remains camelCase.

# handler.py is the orchestrator. `runtime.handler` points here,
# and `blocks run` calls the function named `handler`.
import json
from concurrent.futures import ThreadPoolExecutor

HIRES = ["line_counter", "sentiment_scan", "link_check"]
SUB_TASK_S = 20                 # (60 × 0.7) ÷ 1 sequential step, rounded down


def handler(task, ctx=None):
    text = "\n".join(
        part.text for part in (task.request_parts or []) if part.text
    ).strip()

    if not text:
        raise ValueError("no request text")

    ctx.report_status(f"hiring {len(HIRES)} agents")

    # Run each blocking hire in its own thread. The pool waits for all of them.
    with ThreadPoolExecutor(max_workers=len(HIRES)) as pool:
        settled = list(pool.map(lambda name: hire(ctx, name, text), HIRES))

    results = {}
    missing = []
    for name, outcome in zip(HIRES, settled):
        if outcome["state"] == "completed":
            results[name] = outcome["artifact"]
        else:
            missing.append({"agent": name, "reason": outcome["state"]})

    if not results:
        raise RuntimeError(f"every hire failed: {json.dumps(missing)}")

    ctx.report_status(f"{len(results)}/{len(HIRES)} answered")

    return {"artifacts": [{
        "data": json.dumps({"results": results, "missing": missing}, indent=2),
        "mimeType": "application/json",
    }]}


def hire(ctx, agent_name, text):
    """Submit one sub-task and return a dict. Never raises."""
    session = None
    try:
        session = ctx.task_client.send_message(
            agent_name=agent_name,
            # No owner_id. The SDK uses this agent's identity; forwarding the
            # original caller's identity is rejected.
            request_parts=[{"partId": "request", "text": text}],
            idempotency_key=f"{ctx.task_id}:{agent_name}",
        )

        session.on_progress(
            lambda event: ctx.report_status(f"{agent_name}: {event.message}")
        )

        terminal = session.wait_for_terminal(timeout=SUB_TASK_S)
        if terminal.state != "completed":
            return {"state": terminal.state, "artifact": None}

        artifact = None
        for ref in session.list_artifacts():
            downloaded = session.download_artifact(ref)
            body = downloaded.data.decode("utf-8", errors="replace")
            try:
                artifact = json.loads(body)
            except ValueError:
                artifact = body
        return {"state": "completed", "artifact": artifact}

    except Exception as err:                       # noqa: BLE001, deliberate
        # wait_for_terminal raises on timeout. The remote task keeps running.
        return {"state": f"no result: {err}", "artifact": None}

    finally:
        if session is not None:
            session.close()

What the SDK retries, and what you retry

As in lesson 3, connection failures and task outcomes need different retry policies. The SDK retries only connection failures.

The limits are 600 sendMessage calls per 60 seconds and 1,200 listTasks calls in the same window. Polling and retries around a three-agent fan-out can consume that allowance quickly.

Retries do not fix these configuration and request errors:

  • BillingModeMismatchError, JSON-RPC -32000. Your billingMode does not match how the target agent registered. It carries expected and got. Fix the value before sending the request again.
  • -32602 InvalidParams. The usual cause is a partId that does not appear in the target's io.inputs[].id. Read the card with client.getAgentCard(agentName) instead of guessing.

Streams work only while a task is live. They close at a terminal state, and opening one after that throws StreamUnavailableError. A stream already open keeps draining for 30 seconds after terminal, enough to finish a for await loop but not start one. To receive progress from a long task as well as its result, stream data documents the API. Open the stream before you await the terminal state.

Trusting remote agents

You do not control a remote agent's code or uptime. Your handler chooses the agent, call order, and decision logic. Blocks handles transport and identity. The security documentation covers short-lived per-task JWTs, org-scoped channels, encrypted transport, ownerId validation, and credential isolation: security and compliance, in the security architecture, and the whitepaper. For a security review, include the network whitepaper. These controls protect the connection and caller identity. They do not make the agent's output trustworthy.

Protect the rest of your application at the handler boundary:

  • Treat returned artifacts as untrusted input. They come from a program you may not be able to inspect, and they may become part of a later model prompt. If you paste one into a model turn with write tools, remote text can influence those tools. Parse it, validate the shape declared in io.outputs, and quote it as data rather than as instructions.
  • Allowlist providers and pin agent names you have tested. Catalogue statistics can inform your choice, but a name selected at runtime is still an unreviewed dependency.
  • Check the payload as well as the state. A completed task whose artifact reads {"error": "..."} still failed. The handler above uses this pattern, so the assembly step must inspect the artifact.

Lessons 1 through 3 ran in one process you could inspect. Remote agents add latency and failures outside that process. Give each remote call a stopping condition, or your handler may wait half an hour for an unavailable agent.

For production teams, Blocks Enterprise adds the controls a security review asks for: an admin console, organisations and access control, SSO against your own identity provider, and an audit log of who called what. None of these controls changes the handler. The getting-started page covers the setup, and enterprise support can answer deployment questions.

A2A checklist

  • Declare runtime.maxRunningTimeSec. There is no default ceiling, and this is the wall-clock version of lesson 3's turn cap.
  • Reserve 30% for assembly, then divide the remainder by the longest sequential chain. The number of parallel agents does not determine the wall-clock cap.
  • Fan out with Promise.allSettled, or a thread pool in Python. Represent a failed hire as a missing field.
  • Give every sub-task its own deadline, and remember that your deadline expiring does not stop the remote task.
  • Omit ownerId on sendMessage from inside a handler. Forwarding the original caller's identity is rejected.
  • Pass an idempotencyKey whenever a retry could pay twice for the same work.
  • session.close() in a finally, and client.destroy() when the client is done.
  • Match billingMode to how the target registered, and match partId to its declared io.inputs[].id.
  • Keep your API key server-side. Give a page a tokenEndpoint or tokenProvider.
  • Run blocks check before blocks run, and blocks register (private, free) long before blocks publish.

Break the scaffold on purpose and inspect each error:

  • Rename the agent to my-agent with a hyphen and run blocks check. Read the message; you will see that regex again.
  • In the consumer page, send partId: "req" against a card declaring "request". You should get -32602 without a hint about the mismatched name.
  • Set billingMode: "paid" against your free registered agent. The expected/got pair on BillingModeMismatchError shows both values.
  • Stop blocks run, then submit a task from the page. Watch it wait. It will sit there for 5 minutes before failing agent_unavailable. Set a waitForTerminal deadline.
  • Add a sleep(30_000) to the sub-agent's handler and leave the orchestrator's cap at 20 seconds. Your handler reports a timeout while the sub-agent continues its work. Observe the difference between “I stopped waiting” and “it stopped.”
  • Point one agent at itself in HIRES. Blocks will allow it. Count the tasks.
